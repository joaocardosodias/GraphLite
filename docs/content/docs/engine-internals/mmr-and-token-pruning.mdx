Standard RAG architectures rely on naive **Top-K** retrieval, returning a fixed quantity of document chunks regardless of text length. If individual chunks span 800 tokens each, a Top-5 query injects 4,000 tokens into the LLM context, easily overflowing context windows or displacing system prompt instructions.

Graphite enforces **exact token budget constraints** as a first-class mathematical primitive. Subgraphs are assembled, scored for diversity via **Maximal Marginal Relevance (MMR)**, and greedily pruned to guarantee that synthesized context never breaches the designated token limit.

---

## 1. Token Counting Engine (`TokenCounter`)

Graphite decouples token counting into a flexible abstraction supporting hardware-efficient BPE tokenizers and zero-dependency heuristic fallback counters.

```rust
// crates/graphite-core/src/prompt/token_counter.rs
pub trait TokenCounter: Send + Sync + Debug {
    /// Returns the exact or estimated number of tokens for the given text.
    fn count_tokens(&self, text: &str) -> usize;
}
```

### Supported Encodings

| Counter Type | Underlying Algorithm | Supported Encodings | Performance / Latency |
| :--- | :--- | :--- | :--- |
| **TiktokenCounter** | Native Rust BPE (`tiktoken-rs`) | `cl100k_base` (GPT-4), `o200k_base` (GPT-4o) | Exact BPE token matches; sub-millisecond |
| **HeuristicCounter** | Word boundary & character ratio | Heuristic `max(words, ceil(chars / 4.0))` | Zero allocations, sub-microsecond latency |

```rust
// High-precision BPE counter with OnceLock global caching
impl TokenCounter for TiktokenCounter {
    fn count_tokens(&self, text: &str) -> usize {
        if text.is_empty() {
            return 0;
        }
        self.bpe.encode_with_special_tokens(text).len()
    }
}
```

## 2. Maximal Marginal Relevance (MMR) Optimization

Retrieving documents solely based on relevance often introduces redundant, near-duplicate information (such as multiple amendments of the same legal statute or repetitive code declarations).

Graphite applies **Maximal Marginal Relevance (MMR)** to balance relevance against informational diversity:

```text
MMR_Score(d_i) = lambda * Relevance(d_i) - (1.0 - lambda) * max( Similarity(d_i, d_j) )  for d_j in Selected
```

Where:
* `Relevance(d_i)` is the combined hybrid score (Vector + BM25 + Graph structural score).
* `Similarity(d_i, d_j)` computes lexical overlap between candidate `d_i` and previously selected entities `d_j`.
* `lambda = 0.75` (default) balances high relevance with non-redundant information gain.

### Diversity Parameter Calibration (`lambda`)

* `lambda = 1.0`: Pure relevance ranking. The engine bypasses MMR calculations via a fast path.
* `lambda = 0.75`: Default balanced operation. Penalizes identical passages while maintaining high contextual alignment.
* `lambda = 0.50`: High-diversity exploration. Strongly penalizes semantic overlap, forcing extraction across diverse subgraphs.

## 3. Zero-Allocation Lexical Jaccard Similarity

During MMR selection, pairwise similarities between candidate descriptions are evaluated continuously. Standard token set allocations cause frequent heap churn. Graphite computes lexical overlap via a zero-allocation Jaccard similarity algorithm:

```text
Jaccard(A, B) = |A ∩ B| / |A ∪ B|
```

```rust
// crates/graphite-core/src/prompt/pruner.rs
pub fn prune_subgraph_by_budget_mmr(
    subgraph: &ConnectedSubgraph,
    interner: &StringInterner,
    max_tokens: usize,
    counter: &dyn TokenCounter,
    mmr_lambda: f32,
) -> PrunedSubgraph {
    if subgraph.is_empty() || max_tokens == 0 {
        return PrunedSubgraph::default();
    }

    let lambda = mmr_lambda.clamp(0.0, 1.0);

    // Fast path: bypass MMR overhead when pure relevance is requested
    if (lambda - 1.0).abs() < 1e-4 || subgraph.entities.len() <= 1 {
        return prune_subgraph_by_budget(subgraph, interner, max_tokens, counter);
    }

    // Pre-resolve description slices from StringInterner once
    let descriptions: Vec<&str> = subgraph
        .entities
        .iter()
        .map(|e| {
            if let Some(rec) = e.node_record {
                interner.resolve(rec.description_id).unwrap_or("")
            } else {
                ""
            }
        })
        .collect();

    let n = subgraph.entities.len();
    let mut remaining_indices: smallvec::SmallVec<[usize; 64]> = (0..n).collect();
    let mut mmr_ordered: Vec<ScoredEntity> = Vec::with_capacity(n);
    let mut selected_indices: smallvec::SmallVec<[usize; 64]> = smallvec::SmallVec::with_capacity(n);

    while !remaining_indices.is_empty() {
        let mut best_rem_pos = 0;
        let mut best_mmr_score = f32::NEG_INFINITY;

        for (rem_pos, &cand_idx) in remaining_indices.iter().enumerate() {
            let relevance = subgraph.entities[cand_idx].final_score;
            let cand_desc = descriptions[cand_idx];

            let max_sim = if selected_indices.is_empty() {
                0.0
            } else {
                selected_indices
                    .iter()
                    .map(|&sel_idx| text_jaccard_similarity(cand_desc, descriptions[sel_idx]))
                    .fold(0.0f32, f32::max)
            };

            let mmr_score = (lambda * relevance) - ((1.0 - lambda) * max_sim);
            if mmr_score > best_mmr_score {
                best_mmr_score = mmr_score;
                best_rem_pos = rem_pos;
            }
        }

        let chosen_idx = remaining_indices.swap_remove(best_rem_pos);
        selected_indices.push(chosen_idx);
        mmr_ordered.push(subgraph.entities[chosen_idx].clone());
    }

    let mmr_subgraph = ConnectedSubgraph {
        entities: mmr_ordered,
        edges: subgraph.edges.clone(),
        seed_ids: subgraph.seed_ids.clone(),
    };

    prune_subgraph_by_budget(&mmr_subgraph, interner, max_tokens, counter)
}
```

Stack-allocated `SmallVec<[usize; 64]>` buffers maintain index tracking entirely in CPU registers and L1 cache for subgraphs with up to 64 entities, bypassing dynamic heap allocations.

## 4. Greedy Budget Pruning & Truncation

Once candidates are re-ordered by MMR, the greedy pruner packs entities and their connecting edges into the output buffer until `max_tokens` is reached.

```rust
// Struct representing the finalized prompt context
pub struct PrunedSubgraph {
    pub entities: Vec<ScoredEntity>,
    pub edges: Vec<EdgeRecord>,
    pub total_tokens: usize,
    pub budget: usize,
}
```

### Pruning Mechanics

1. **Header Accounting:** Fixed header tokens (`# Retrieved Knowledge Context:\n`) are accounted for before processing entities.
2. **Greedy Entity Assembly:** Formats candidate entity strings, measures exact token expenditure, and admits the entity if `current_tokens + entity_tokens <= max_tokens`.
3. **Top Match Graceful Truncation:** If the single highest-scoring entity slightly exceeds the total budget, the engine gracefully truncates its text description to utilize all remaining token capacity rather than returning an empty context.
4. **Relational Edge Pruning:** Connecting edges are admitted only if both source and target endpoints were successfully included within the token budget.
